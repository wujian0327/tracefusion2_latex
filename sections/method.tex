TraceFusion~2 answers a question about one execution: which instances of
declared source fields contributed data to a particular response field?
It plans observations before deployment, collects facts while the application
executes, and reconstructs dependencies offline. The same query guides both
collection and reconstruction. In selective mode, the collector can omit
certain values or observations, but it must retain the evidence that lets
the reconstructor verify those omissions.

\subsection{Running Example and Query Semantics}
\label{sec:method-query}

Consider the Mall administrator login, simplified in
Fig.~\ref{fig:login-example}. We ask which instance of the authentication
client's return field supplies the response leaf \texttt{/data/expiresIn}.
The intervening login-log operation writes to the database and may update
other state. Treating that operation as read-only would be incorrect.
Invalidating all preceding dependencies would also lose an answer whenever
the operation cannot reach the token result. A second problem is that two
authentication calls can return equal expiration values: neither the
response value nor its field name identifies which call produced it.

\caption{Simplified Mall login. The query follows the actual token result to

\label{fig:login-example}
\end{figure}

A query is $Q=(e,t,\pi,B)$, where $e$ is the entry method, $t$ is the
target JVM field (or a field anchoring a supported container path), $\pi$
is the response path, and $B$ is the set of declared source boundaries.
A wildcard selects one target instance for each actual matching member.
A source boundary may admit an entry input, a specified mapper or cache
read, or a field at a supported RPC boundary. It is a stopping point:
a query that declares a mapper return does not ask for the history of the
database row. Likewise, the login query stops at the client return rather
than the earlier network message.

A storage coordinate is $(p,o,f,v)$: process $p$, object identity $o$
within that process, declaring field $f$, and observed write version $v$.
A source occurrence also identifies the observation and, for a declared
call, its actual call ID and caller site. Container elements use an
appropriate member coordinate and observed content stage. A field can
therefore be observed by two distinct calls without becoming one source,
and a successful write advances the version even if the new value equals
the old one. The answer reports explicit data origins. It records branch,
index, and filtering evidence separately to explain which path or member
was selected; it does not claim general implicit-flow tracking. Unlike a
statement slice such as Mandoline's~\cite{ahmed2021mandoline}, the answer is
a set of declared field-source occurrences.

\subsection{Planning Observations for the Target}
\label{sec:method-planning}

The planner takes the original bytecode model, $Q$, and the available
deployment evidence. It resolves the target binding, preserves the
declared sources, and checks candidate reconstruction strategies against
the operations, class definitions, and runtime conditions each strategy
requires. A specialized strategy may handle a copy or a mapped reduction;
the common execution kernel handles broader supported calls and effects.
A candidate can remain conditional when the actual dispatch or a library
contract still needs runtime evidence. Admission does not establish that
the query has a known answer.

For the common kernel, possible definitions of operand-stack and local
slots are propagated through the admitted control-flow graph. At a join,
the planner unions alternative definitions in corresponding slots; it
retains a local definition only where the slot is initialized on every
incoming path. A bounded worklist propagates changes along normal and
supported exceptional edges. From the target, a backward traversal records
possible operand dependencies. The planner conservatively extends the
field-value requirements to include interpreted field reads, checked
accessors and constructor projections, and the full inputs of finite
decoder or conversion rules where needed.

The plan distinguishes three obligations: values needed for computation,
effects that can change the relevant state, and evidence needed to verify
the explanation. A value-only traversal cannot establish the latter two:
an unused call can publish an alias or throw into a handler that supplies
the response. The plan therefore also retains the required writes and
versions, references, membership and selection, call completion, source
occurrences, target binding, and communication evidence. An omission
candidate specifies a location, a permitted observation, and a runtime
guard. The planner does not compute a minimum slice or remove business
instructions.

\subsection{Collecting and Verifying Execution Facts}
\label{sec:method-evidence}

A Java agent instruments the application at class loading. It records
actual implementations, frames, call sites, receivers and arguments,
normal and exceptional completions, and the field and container events
required by the plan. The original application still executes; the agent
does not propagate source sets online as MirrorTaint does~\cite{ouyang2023mirrortaint}.
Separating collection from analysis also appears in
StraightTaint~\cite{ming2016straighttaint}; here the plan is specialized to
the response field and retains the evidence needed for field-instance
binding and checking omissions. A call ID connects start
to completion and distinguishes repeated or nested calls at one site.
For a declared source call, the offline checker additionally matches the
caller and instruction position, the invocation interval, and the
returned object's observed field version. A snapshot without this match
cannot establish a call-return source.

Message identity is independent of request ancestry. In supported HTTP
paths, client send, client receive, server receive, and server send carry
distinct roles; a child client response cannot borrow the root request's
identity. A cross-service edge requires a unique compatible message pair
with the expected direction and field path, plus evidence relating the
decoded field to its local object and version. Similarly, the response
leaf must bind to the actual returned object or member and its version.
A return snapshot supplies target evidence, not a new source. Retained
HTTP bytes alone do not identify the assignments made by a decoder.

Before interpreting a capture, the offline checker checks plan identity,
event order, call and message closure, and recorded collector failures.
An incomplete or contradictory required record invalidates certification
for the affected capture. By contrast, an intact capture can still be
insufficient to explain the effects of a call.

\subsection{Reconstructing Dependencies and Effects}
\label{sec:method-kernel}

The offline kernel follows the observed path through the supported
bytecode. It tracks the stack and locals for each frame, and shares
field and container state across related frames. For each value it maintains
data origins $D$, selection evidence $C$, and an unresolved flag $u$,
alongside the observed scalar or reference information used for checks.
A verified source occurrence $b$ contributes $D=\{b\}$. An interpreted
constant has $D=\varnothing$ and $u=0$; an opaque result may have no
recorded origins but has $u=1$. Supported arithmetic unions the origins
of the actual operands and propagates their uncertainty. A container
read inherits the chosen member's data origins; the index or predicate
that selected it contributes to selection evidence. A field write installs
the new dependency state at the observed version. Thus a known constant
overwrite removes the old origins even when the field value is unchanged.

\subsubsection{Contracts for framework operations}
\label{sec:method-effects}

A finite contract specifies the implementation and configuration it covers,
the facts required from the actual call, and the resulting state transfer
or effect. For example, a list copy may retain the existing member states
only after the contract establishes that the supported branch returned
the same members in the observed order, without a conversion callback.
A fresh list does not make its members private. When only a forwarding
step is verified, it retains existing origins rather than creating a new
source. Missing applicability evidence leaves the operation opaque; a
contradiction in required capture evidence is handled by the integrity
checks.

\subsubsection{Restricting the effects of an opaque call}

When no interpretation or contract explains a necessary call, the
reconstructor marks its result unresolved and conservatively invalidates
state the call may change. Conceptually, for call $c$ in modeled heap $H$,
the affected objects are bounded by
\begin{equation}
   A_c=\operatorname{Reach}_H(R_c\cup N_c),
   \label{eq:effect-reach}
\end{equation}
where $R_c$ includes receiver and reference argument roots and $N_c$
includes nonlocal and published roots. Reachability includes supported
field, wrapper, container, and capture links. The rule is about the modeled
heap, not a guarantee about arbitrary reflective, native, or concurrent
writes.

A source object is nonlocal by default. A reviewed locality contract can
remove a particular returned object graph from those nonlocal roots once
the actual call, fresh allocations, supported construction or decoding,
and unexposed return path have been verified. This changes the effect
bound, not the source coordinate. If a later call can reach the graph
through an argument, a wrapper, or publication, it can again invalidate
the relevant state. The version staying the same is not a locality check.
A later, independently verified source read can establish new origins
after an opaque effect; it cannot recover an earlier unresolved origin.

In Fig.~\ref{fig:login-example}, the checked authentication return
supplies the occurrence $b$. If the token graph remains outside $A_c$
for the logging call, its provenance survives even though the call
writes elsewhere. If a wrapper carrying that token is passed into the
opaque call, the reachability check no longer protects it. Both executions
can return the same expiration value; the monitor must distinguish them
by the actual references and effects.

\subsection{Guarded Reduction of Observations}
\label{sec:method-reduction}

Full and selective modes use the same rules for provenance. Full means
the reference observation policy for the planned query, not a trace of
the entire JVM. We distinguish the following three reductions from
response-only persistence and optimizations shared by both modes.
None skips an application operation.

Table~\ref{tab:observation-policy} separates three permissions. For
value projection, the planner excludes all fields required by the target
or an admitted consumer, including a finite conversion that needs its
complete input projection. For the method-body rule, simply returning
the same object is insufficient: after the candidate call, the caller
and its forwarding ancestors must only forward references. A later
field read, container computation, invocation, or handler can depend on
the call's effects and disqualifies the region. The planner also excludes
prefix constructors that may pass the source reference to unmodeled code.
At the call, the runtime guard checks the actual source occurrence, the
locality witness, and the absence of exposure to the receiver and
arguments.

\paragraph{Why the retained evidence matters}
The collector tests eligibility before the first omission and collects
the original observations if the guard is unavailable or false.
The offline checker verifies the plan's permission, the actual scope and
witnesses, and the recorded omissions. A witness established later cannot
authorize an earlier omission. If the remaining records contradict an
omission that already occurred, the checker rejects the evidence.

For the rules above, the preservation argument is local. An eligible
payload omission removes no value required by a checked transfer, while
the version and identity transitions still occur. An eligible body
omission protects the forwarded source graph from the call and admits no
subsequent target computation that consumes the unobserved internal state.
The call's completion and possible effects still participate in the
reconstruction. Under these premises, the target-relevant transitions
retain the same source occurrences and selection evidence as the full
policy for that execution. This argument does not establish equivalence
for arbitrary Java programs, or the correctness of a source answer simply
because the two modes agree.

\subsection{Binding the Answer and Reporting Limits}
\label{sec:method-graph}

Reconstruction connects verified local providers and message links in a
dependency graph and binds each actual target occurrence $x$ to its
provider. The result, when known, is the set of reachable declared source
occurrences,
\begin{equation}
    \operatorname{Origins}_Q(x)
      = \{b \in \mathcal{S}_B \mid x \leadsto b\},
    \label{eq:answer}
\end{equation}
where $\mathcal{S}_B$ contains only the observations admitted by $B$
for this execution. In the unexposed login case, the reported origin
is $b$, with its actual invocation and field version. A supported
constant target can instead have a known empty source set.

An unresolved dependency yields \texttt{unknown}; a plan rejection,
analysis limit, or invalid capture is reported separately. A normal
execution with no matching target member produces no answer instance,
whereas an actual null leaf is still a target. The method is limited to
the modeled JVM operations, supported bindings, and applicable reviewed
contracts. Framework configuration changes, unmodeled callbacks, and
reflective, native, or shared concurrent writes can invalidate the
premises. The method does not infer origins from equal values when
these premises are absent.
